# Demonstrations

The portable viewer contains three recordings from two experiments. Select **Open demonstration** and use **Run** to choose a recording. The data is generated by simulators, with independent evaluation seeds and declared return conventions.

## Rocket Landing · PPO

- In **Training**, scrub from checkpoint `0` to `3120`. Landing success rises from 1/200 to 200/200 on the same held-out scenarios. Training also shows recorded evaluation return and the gap to the feedback controller. The return uncertainty is across evaluation episodes.
- In **Policy**, select the position–height slice to compare commands at different checkpoints.
- At checkpoint `3120`, open **Network → Geometry**. Choose `position-height-slice`, rows `12` and `54`, and **Hidden 2** to compare the layer representations.
- In **Dynamics**, choose a recorded evaluation episode. Open **Environment** and use its episode controls to replay the flight and follow the telemetry. **Compare matched benchmark** opens the feedback controller's flight from the same initial scenario.

The controller observes normalized position, velocity, attitude, angular rate, fuel and time, then chooses throttle and attitude command. The engine advances a planar physical model in substeps. Landing success requires position, velocity and attitude within the declared tolerances. The feedback controller is an engineered benchmark. It landed in 200/200 held-out scenarios. No global optimality claim is made.

PPO uses 16 lanes, 240-decision rollouts, two 64-unit hidden layers and discount 0.99. The bundled seed uses 12,480 vector steps, or 199,680 factual transitions. The augmented recording adds 200 independently evaluated scenarios per retained checkpoint through historical policy restoration.

## Alpha Execution

**Alpha Execution · Expected Return** and **Alpha Execution · CVaR** use the same stylized stochastic-control model. They have 12 decisions. At each decision the policy chooses target inventory and pays linear spread and quadratic temporary impact. Execution consumes some available alpha before the next price move. Post-trade inventory earns that move, and any inventory remaining after the last move is liquidated. Reward and P&L are simulated in normalized units. [Model equations](alpha-execution-design.md)

1. Open **Policy** and select `inventory-alpha-slices` row `8` to inspect the inventory–alpha map and the selected-input comparison. **Alpha Grid DP** is a numerical grid benchmark with 31 inventory points, 161 alpha points, 61 target actions and nine Gaussian nodes.
2. Open **Value** in the expected-return recording. At checkpoint `19991`, select `conditional-alpha` row `2`, with inventory `0`, available alpha `+0.3` and the full 12-decision horizon remaining. Set target inventory to `+0.5`. Turn on the numerical reference to see its separate action-value comparison.
3. In the conditional CDF, the critic forecast has mean `1.184354` and standard deviation `0.291883`. Its 512 matched futures have mean `1.288344`, standard deviation `1.210202`, and mean standard error `0.053484`. These futures execute the same forced first trade and continue with the frozen deterministic target policy at checkpoint `19991`. The numerical benchmark follows its own controller. [Matched Value screenshot](images/value.png)
4. Switch to **Alpha Execution · CVaR**, compare the policies, and inspect recorded trades, inventory, costs and P&L in **Environment**. CVaR uses a lower-tail actor objective. The conditional critic distribution still describes total environmental return under its recorded continuation.

The calibration example measures one condition. It shows that the spread of the forecast can be too narrow even when its mean is much closer. Checkpoint, input, first action and continuation must all match to score a forecast. An unavailable calibration panel usually means that the recording lacks compatible conditional evidence for the current selection.

## Reproduce the recordings

The archive includes the verified original recordings and per-file SHA-256 inventories. Reproduction is optional. Use fresh paths for the commands below. Output is written locally and the training examples report progress.

```sh
cargo run --locked -p rust-rl --features diagnostics --example diagnostic_session -- planar-ppo runs/public-rocket detailed --steps=12480 --seed=7 --reference --render --evaluation-episodes=200 --evaluation-seed=900000
cargo run --release --locked -p rust-rl --features diagnostics --example diagnostic_session -- rocket-history runs/public-rocket-history --source=runs/public-rocket --evaluation-episodes=200 --evaluation-seed=900000
cargo run --locked -p rust-rl --features diagnostics --example diagnostic_session -- alpha-d4pg runs/public-alpha-expected detailed --steps=20000 --seed=11 --reference --evaluation-episodes=1000 --evaluation-seed=1800000 --rich-conditional
cargo run --locked -p rust-rl --features diagnostics --example diagnostic_session -- alpha-cvar runs/public-alpha-cvar detailed --steps=20000 --seed=11 --reference --evaluation-episodes=1000 --evaluation-seed=1800000 --rich-conditional
```

Open the generated recording or verify it headlessly. Replace the path to inspect another recording.

```sh
cargo run --locked --release -p rl-viewer -- --check runs/public-rocket-history
cargo run --locked --release -p rl-viewer -- runs/public-rocket-history
```

Run metadata and timestamps can cause file hashes to differ across independently generated runs. The bundled checksums identify the specific distributed bytes. Use the supplied PowerShell script to generate a comparable file inventory.

```powershell
./scripts/hash-recording.ps1 -Recording runs/public-rocket-history -Output rocket.sha256
```
